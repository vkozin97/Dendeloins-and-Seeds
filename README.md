# Dendeloins-and-Seeds

Investigation on the "Dendeloins and Seeds" paper game





\# Dandelions Solver



Точный исследовательский решатель для игры «Одуванчики и семена».



Цель проекта — разработать инструмент, который позволяет для заданных параметров игры определить победителя при оптимальной игре обоих игроков, восстановить оптимальные стратегии и собрать статистику сложности перебора. Проект должен начинаться с малых размеров поля и постепенно масштабироваться к более сложным случаям, включая базовый вариант `6 × 6`.



\---



\## 1. Краткое описание игры



Есть квадратное поле размера `n × n`, состоящее из клеток.



Играют два игрока:



\* \*\*Игрок 1\*\* сажает одуванчики.

\* \*\*Игрок 2\*\* выбирает направления ветра.



Игра идёт `k` раундов. Значения `n` и `k` являются параметрами исследования.



В каждом раунде:



1\. Игрок 1 выбирает клетку поля и сажает туда новый одуванчик.

2\. Игрок 2 выбирает одно из ещё не использованных направлений ветра.

3\. Все одуванчики, которые находятся на поле после посадки игрока 1, выпускают семена в выбранном направлении до края поля.

4\. Семена остаются на поле навсегда.

5\. Выбранное направление ветра считается использованным и не может быть выбрано повторно.



После `k` раундов проверяется результат:



\* Игрок 1 выигрывает, если все клетки поля заняты одуванчиками или семенами.

\* Игрок 2 выигрывает, если после `k` раундов осталась хотя бы одна пустая клетка.



Также если все клетки оказались заняты раньше окончания `k` раундов, состояние уже считается выигрышным для игрока 1, потому что занятость клеток дальше только увеличивается.



\---



\## 2. Точные правила, которые используются в проекте



\### 2.1. Посадка одуванчика



Игрок 1 может посадить одуванчик в любую клетку, где ещё нет одуванчика.



При этом:



\* посадить одуванчик в пустую клетку можно;

\* посадить одуванчик в клетку с семенем можно;

\* посадить одуванчик в клетку, где уже есть одуванчик, нельзя.



Клетка с одуванчиком считается занятой.



\### 2.2. Семена



Семена появляются только в результате действия ветра.



Семена сами не распространяются. Источниками новых семян являются только одуванчики.



Если семя попадает в клетку, которая уже занята семенем или одуванчиком, состояние клетки не меняется.



\### 2.3. Направления ветра



Всего есть 8 направлений:



```text

0: E   — вправо

1: W   — влево

2: N   — вверх

3: S   — вниз

4: NE  — вверх-вправо

5: NW  — вверх-влево

6: SE  — вниз-вправо

7: SW  — вниз-влево

```



Точное соответствие индексов направлениям можно изменить, но оно должно быть единым во всей программе и явно зафиксированным в коде.



Каждое направление может быть использовано максимум один раз за игру.



Следовательно, при стандартных 8 направлениях обычно предполагается `k ≤ 8`. Если в будущем потребуется исследовать `k > 8`, необходимо явно расширить правила.



\### 2.4. Важное правило о времени посадки



Новый одуванчик не распространяет семена по направлениям ветра, которые были использованы до его посадки.



Например:



1\. В первом раунде был использован ветер вправо.

2\. Во втором раунде игрок посадил новый одуванчик.

3\. Новый одуванчик уже никогда не распространит семена вправо, потому что направление вправо было использовано раньше и не может повториться.

\## 3. Математическая постановка



Это конечная детерминированная игра с полной информацией и без случайности.



Для фиксированных параметров `n` и `k` нужно ответить на вопрос:



> Может ли игрок 1 гарантированно заполнить всё поле за `k` раундов при оптимальной игре игрока 2?



Состояние игры описывается тремя основными объектами:



```text

D — множество клеток с одуванчиками

O — множество занятых клеток: одуванчики + семена

U — множество уже использованных направлений ветра

```



Инвариант:



```text

D ⊆ O

```



Игрок 1 выигрывает из состояния, если существует такая посадка, что при любом допустимом ответе игрока 2 состояние остаётся выигрышным для игрока 1.



Логика рекурсии:



```text

Win(D, O, U) = true, если O покрывает всё поле.



Win(D, O, U) = false, если число уже использованных направлений равно k,

&#x20;                   но поле ещё не полностью покрыто.



Иначе:



Win(D, O, U) = существует допустимая клетка p,

&#x20;              такая что для любого доступного направления dir:

&#x20;                  Win(next\_state(D, O, U, p, dir)) = true

```



В терминах кванторов:



```text

Игрок 1 выигрывает ⇔

∃ посадка p:

&#x20;   ∀ доступное направление dir:

&#x20;       следующее состояние выигрышно для игрока 1

```



Игрок 2 выигрывает, если:



```text

∀ посадка p:

&#x20;   ∃ доступное направление dir:

&#x20;       следующее состояние проигрышно для игрока 1

```

\## 4. Общая стратегия реализации



Проект должен реализовывать точный решатель, а не эвристическую симуляцию.



Основные обязательные оптимизации:



1\. Битовые маски для хранения клеток.

2\. Предрасчёт лучей распространения семян.

3\. Мемоизация состояний.

4\. Alpha-beta-подобное отсечение для булевого minimax.

5\. Канонизация состояний через симметрии квадратного поля.

6\. Сбор подробной статистики поиска.

7\. Возможность восстановления найденной стратегии.



Целевая реализация — C++.



Python может использоваться только для вспомогательных скриптов, визуализаций или анализа результатов, но не как основной движок полного перебора.

\## 5. Представление поля и координат



\### 5.1. Размер поля



Поле имеет размер:



```text

n × n

```



Количество клеток:



```text

m = n²

```



Для базового варианта `n = 6`, значит `m = 36`.



Для эффективной реализации предполагается, что `m ≤ 64`, чтобы поле можно было хранить в `uint64\_t`.



Если в будущем потребуется `n > 8`, понадобится другое представление масок, например несколько `uint64\_t` или динамический bitset.



\### 5.2. Индексация клеток



Рекомендуемая индексация:



```text

cell\_id = y \* n + x

```



где:



```text

x = 0..n-1 — координата по горизонтали слева направо

y = 0..n-1 — координата по вертикали снизу вверх или сверху вниз

```



Важно: выбранную систему координат нужно один раз зафиксировать и использовать везде одинаково.



Для битовой маски:



```cpp

uint64\_t bit = 1ULL << cell\_id;

```



Клетка входит в маску, если соответствующий бит равен `1`.



\### 5.3. Рекомендуемые маски состояния



Основное состояние:



```cpp

struct State {

&#x20;   uint64\_t dandelions;    // D: клетки с одуванчиками

&#x20;   uint64\_t occupied;      // O: все занятые клетки: одуванчики + семена

&#x20;   uint8\_t used\_dirs;      // U: использованные направления ветра

};

```



Инварианты:



```text

(dandelions \& \~occupied) == 0

occupied != 0 после первой посадки

used\_dirs содержит не более k битов

```



Текущий номер раунда можно не хранить отдельно, если он равен количеству использованных направлений:



```cpp

round = popcount(used\_dirs);

```

\## 6. Предрасчёт распространения семян



Для каждой клетки и каждого направления нужно заранее посчитать маску луча:



```cpp

uint64\_t ray\[cell\_id]\[dir];

```



`ray\[cell\_id]\[dir]` содержит все клетки от данной клетки до края поля в направлении `dir`, не включая саму клетку с одуванчиком.



Например, для поля `6 × 6`, если одуванчик стоит в клетке `(2, 3)`, а направление — вправо, то луч содержит клетки:



```text

(3, 3), (4, 3), (5, 3)

```



при нулевой индексации, или:



```text

(3, 3), (4, 3), (5, 3), (6, 3)

```



при пользовательской индексации от 1.



\### 6.1. Расчёт результата ветра



После посадки игрока 1 есть маска одуванчиков `D`.



Для выбранного направления `dir` нужно получить маску всех клеток, которые будут засеяны:



```cpp

uint64\_t blow(uint64\_t D, int dir) {

&#x20;   uint64\_t result = 0;

&#x20;   for each cell in D:

&#x20;       result |= ray\[cell]\[dir];

&#x20;   return result;

}

```



Следующее занятое множество:



```cpp

occupied2 = occupied1 | blow(dandelions1, dir);

```



\### 6.2. Ускорение blow



Базовая версия может проходить по установленным битам `D`.



Оптимизированный вариант может кэшировать результат:



```text

blow\_cache\[(D, dir)] -> uint64\_t

```



Но кэш `blow` надо вводить аккуратно: количество разных `D` может быть большим. На первом этапе достаточно реализовать быстрый перебор установленных битов через `ctz`/`pop\_lsb`.

\## 7. Minimax и alpha-beta-подобное отсечение



Так как результат состояния булевский, классический числовой minimax не нужен. Нужна рекурсия вида `canFirstWin(state)`.



\### 7.1. Базовые случаи



```cpp

bool canFirstWin(State state) {

&#x20;   if (state.occupied == full\_board\_mask) {

&#x20;       return true;

&#x20;   }



&#x20;   if (popcount(state.used\_dirs) == k) {

&#x20;       return false;

&#x20;   }



&#x20;   ...

}

```



\### 7.2. Ход игрока 1



Игрок 1 выбирает клетку, где ещё нет одуванчика:



```text

plantable = full\_board\_mask \& \~dandelions

```



Важно: клетки с семенами доступны для посадки, поэтому запрещаются только клетки с одуванчиками, а не все занятые клетки.



\### 7.3. Ход игрока 2



Игрок 2 выбирает направление, которое ещё не было использовано:



```text

available\_dirs = all\_dirs\_mask \& \~used\_dirs

```



Но если `k < 8`, игра завершается после `k` раундов, даже если не все направления использованы.



\### 7.4. Булевское отсечение



Псевдокод:



```cpp

bool canFirstWin(State state) {

&#x20;   state = canonicalize(state);



&#x20;   if (memo contains state) {

&#x20;       return memo\[state];

&#x20;   }



&#x20;   if (state.occupied == full\_board\_mask) {

&#x20;       memo\[state] = true;

&#x20;       return true;

&#x20;   }



&#x20;   if (popcount(state.used\_dirs) == k) {

&#x20;       memo\[state] = false;

&#x20;       return false;

&#x20;   }



&#x20;   for each candidate planting cell p in ordered order:

&#x20;       State afterPlant = state;

&#x20;       afterPlant.dandelions |= bit(p);

&#x20;       afterPlant.occupied   |= bit(p);



&#x20;       bool plantingWinsAgainstAllWinds = true;



&#x20;       for each available dir in ordered order:

&#x20;           State next = afterPlant;

&#x20;           next.occupied |= blow(next.dandelions, dir);

&#x20;           next.used\_dirs |= dir\_bit(dir);



&#x20;           if (!canFirstWin(next)) {

&#x20;               plantingWinsAgainstAllWinds = false;

&#x20;               break; // игрок 2 нашёл опровержение этой посадки

&#x20;           }

&#x20;       }



&#x20;       if (plantingWinsAgainstAllWinds) {

&#x20;           memo\[state] = true;

&#x20;           best\_move\[state] = p;

&#x20;           return true; // игрок 1 нашёл выигрышную посадку

&#x20;       }

&#x20;   }



&#x20;   memo\[state] = false;

&#x20;   return false;

}

```



Это и есть alpha-beta-подобное отсечение:



\* игрок 1 прекращает перебор посадок, когда нашёл одну гарантированно выигрышную;

\* игрок 2 прекращает перебор ветров, когда нашёл один ответ, ломающий текущую посадку.

\## 8. Мемоизация



\### 8.1. Назначение



Мемоизация нужна, чтобы не пересчитывать одно и то же состояние много раз.



Ключ состояния:



```text

canonical(dandelions, occupied, used\_dirs)

```



Значение:



```text

true  — игрок 1 может гарантированно выиграть из состояния

false — игрок 1 не может гарантированно выиграть из состояния

```



\### 8.2. Рекомендуемая структура ключа



Для `n ≤ 8`:



```cpp

struct StateKey {

&#x20;   uint64\_t dandelions;

&#x20;   uint64\_t occupied;

&#x20;   uint8\_t used\_dirs;

};

```



Для hash map нужно реализовать быстрый хэш.



Рекомендуется рассмотреть специализированные быстрые hash map-реализации вместо стандартного `std::unordered\_map`, например:



\* `ankerl::unordered\_dense`

\* `robin\_hood::unordered\_flat\_map`

\* `absl::flat\_hash\_map`



Но первая версия может использовать `std::unordered\_map`, если важна простота.



\### 8.3. Что хранить в memo



Минимально:



```text

StateKey -> bool result

```



Для восстановления стратегии дополнительно:



```text

StateKey -> best planting cell, если state выигрышный для игрока 1

```



И желательно:



```text

StateKey + candidate planting cell -> refuting wind direction,

если эта посадка проигрышна из-за ответа игрока 2

```



Практический вариант:



```cpp

struct MemoEntry {

&#x20;   bool solved;

&#x20;   bool first\_wins;

&#x20;   int8\_t best\_plant\_cell;      // -1 если нет

&#x20;   int8\_t refuting\_direction;   // -1 если не применимо или не сохраняется

};

```



Для экономии памяти стратегию можно сохранять не для всех состояний, а только при отдельном режиме `--store-strategy`.

\## 9. Канонизация состояния



\### 9.1. Зачем нужна канонизация



Многие состояния эквивалентны с точностью до симметрий квадратного поля.



Например:



\* одуванчик в левом верхнем углу и использованный ветер вправо;

\* одуванчик в правом верхнем углу и использованный ветер влево.



Это одна и та же стратегическая ситуация после отражения поля по вертикали.



Без канонизации решатель будет считать такие состояния отдельно.



\### 9.2. Симметрии квадратного поля



Используются 8 симметрий:



```text

0\. identity

1\. rotate 90

2\. rotate 180

3\. rotate 270

4\. reflect vertical

5\. reflect horizontal

6\. reflect main diagonal

7\. reflect anti-diagonal

```



Для каждой симметрии нужно уметь преобразовывать:



1\. клеточные маски `dandelions` и `occupied`;

2\. маску использованных направлений `used\_dirs`.



\### 9.3. Преобразование клеток



Для каждой симметрии `sym` и каждой клетки `cell\_id` заранее рассчитывается:



```cpp

int transformed\_cell\[sym]\[cell\_id];

```



Тогда преобразование маски:



```cpp

uint64\_t transformMask(uint64\_t mask, int sym) {

&#x20;   uint64\_t result = 0;

&#x20;   while (mask) {

&#x20;       int cell = pop\_lsb(mask);

&#x20;       result |= 1ULL << transformed\_cell\[sym]\[cell];

&#x20;   }

&#x20;   return result;

}

```



\### 9.4. Преобразование направлений



Для каждой симметрии и каждого направления заранее рассчитывается:



```cpp

int transformed\_dir\[sym]\[dir];

```



Тогда:



```cpp

uint8\_t transformDirs(uint8\_t used\_dirs, int sym) {

&#x20;   uint8\_t result = 0;

&#x20;   for dir in 0..7:

&#x20;       if (used\_dirs \& (1 << dir)) {

&#x20;           result |= 1 << transformed\_dir\[sym]\[dir];

&#x20;       }

&#x20;   return result;

}

```



\### 9.5. Лексикографическая канонизация



Для состояния `(D, O, U)` строятся 8 симметричных вариантов:



```text

(D\_0, O\_0, U\_0)

(D\_1, O\_1, U\_1)

...

(D\_7, O\_7, U\_7)

```



Каноническим состоянием считается минимальное лексикографически.



Рекомендуемый порядок сравнения:



```text

1\. occupied

2\. dandelions

3\. used\_dirs

```



То есть состояние `A` меньше состояния `B`, если:



```text

A.occupied < B.occupied

или A.occupied == B.occupied и A.dandelions < B.dandelions

или A.occupied == B.occupied и A.dandelions == B.dandelions и A.used\_dirs < B.used\_dirs

```



Почему `occupied` первым:



\* именно занятые клетки определяют близость к победе;

\* эта маска обычно более плотная и лучше различает состояния на поздних этапах;

\* но технически допустим и другой стабильный порядок, если он используется последовательно.



\### 9.6. Обратное преобразование для стратегии



Если стратегия хранится для канонического состояния, то при выводе стратегии для исходного состояния нужно знать, какая симметрия была применена.



Поэтому функция канонизации должна уметь возвращать не только канонический ключ, но и номер симметрии:



```cpp

struct CanonicalResult {

&#x20;   StateKey key;

&#x20;   int sym; // симметрия, которая перевела исходное состояние в каноническое

};

```



Если в каноническом состоянии лучший ход — клетка `p\_canon`, то для исходного состояния нужно применить обратную симметрию:



```text

p\_original = inverse\_transform\_cell\[sym]\[p\_canon]

```



Аналогично, если нужно показать направление ветра в исходной системе координат:



```text

dir\_original = inverse\_transform\_dir\[sym]\[dir\_canon]

```

\## 10. Упорядочивание ходов



Хороший порядок перебора может радикально влиять на скорость из-за отсечений.



\### 10.1. Посадки игрока 1



Сначала стоит проверять клетки, которые выглядят наиболее перспективными.



Возможные эвристики:



1\. Клетки, которые дают большой потенциальный прирост покрытия по оставшимся направлениям.

2\. Центральные клетки.

3\. Клетки, которые покрывают труднодостижимые зоны.

4\. Клетки, которые максимизируют минимум прироста по ответам игрока 2.



Простая стартовая эвристика:



```text

score\_plant(p) = sum over available dirs of popcount(ray\[p]\[dir] \& \~occupied)

```



Но нужно помнить, что после посадки новый одуванчик будет участвовать только в будущих ветрах, а уже использованные направления не повторятся.



Более сильная эвристика:



```text

score\_plant(p) = min over available dirs of

&#x20;                popcount((blow(D ∪ {p}, dir)) \& \~occupied)

```



Эта эвристика ориентирована на худший ответ игрока 2.



\### 10.2. Направления игрока 2



Игрок 2 пытается найти опровергающий ветер.



Поэтому сначала стоит проверять направления, которые дают игроку 1 наименьший прирост покрытия:



```text

score\_dir(dir) = popcount(blow(D, dir) \& \~occupied)

```



Направления сортируются по возрастанию `score\_dir`.



Если первый же слабый ветер ведёт к проигрышному для игрока 1 состоянию, остальные ветры проверять не нужно.

\## 11. Оценки и отсечения по достижимости



Помимо minimax желательно добавить быстрые проверки, которые позволяют заранее отбросить заведомо проигрышные состояния.



\### 11.1. Немедленная победа



Если поле полностью занято:



```cpp

if (occupied == full\_board\_mask) return true;

```



\### 11.2. Завершение игры



Если сделано `k` раундов и поле не полностью занято:



```cpp

if (popcount(used\_dirs) == k) return false;

```



\### 11.3. Грубая верхняя оценка покрытия



Можно оценить, какие пустые клетки вообще теоретически могут быть покрыты оставшимися ветрами с текущими и будущими одуванчиками.



На первом этапе этот блок можно не реализовывать, но архитектура должна позволять добавлять такие отсечения.



Пример простой верхней оценки:



```text

available\_dirs = directions not in U

optimistic\_cover = occupied



Для каждой ещё возможной посадки p и каждого доступного направления dir:

&#x20;   optimistic\_cover |= ray\[p]\[dir]



Если optimistic\_cover != full\_board\_mask,

&#x20;   то состояние точно проигрышно для игрока 1.

```



Эта оценка очень оптимистична, потому что разрешает использовать слишком много будущих посадок одновременно, но если даже она не покрывает поле, состояние точно безнадёжно.



Более точные оценки можно добавлять позже.

\## 13. Восстановление стратегии



Проект должен поддерживать два режима:



1\. Только определить победителя.

2\. Определить победителя и сохранить стратегию.



Режим стратегии может потреблять больше памяти.



\### 13.1. Если выигрывает игрок 1



Нужно уметь восстановить хотя бы одну гарантирующую победу стратегию:



```text

из каждого выигрышного состояния игрока 1:

&#x20;   какую клетку посадить

```



Поскольку игрок 2 может отвечать разными ветрами, стратегия игрока 1 является деревом, а не одной линейной последовательностью.



\### 13.2. Если выигрывает игрок 2



Нужно уметь показать контрстратегию игрока 2:



```text

на каждую посадку игрока 1:

&#x20;   какой ветер выбрать, чтобы сохранить проигрышность состояния для игрока 1

```



На первом этапе достаточно сохранять только один опровергающий ветер для каждой проверенной проигрышной посадки.



\### 13.3. Форматы вывода стратегии



Возможные форматы:



```text

JSON

текстовое дерево

интерактивный просмотрщик в будущем

```



Стартовый формат — JSON.



Примерная структура:



```json

{

&#x20; "n": 6,

&#x20; "k": 7,

&#x20; "winner": "P1",

&#x20; "strategy": {

&#x20;   "state\_key": "...",

&#x20;   "best\_plant": \[2, 3],

&#x20;   "responses": {

&#x20;     "E": { "next\_state": "..." },

&#x20;     "N": { "next\_state": "..." }

&#x20;   }

&#x20; }

}

```

\## 17. Оценка сложности



Для `n = 6`, `k = 7`:



```text

m = 36

```



Количество возможных последовательностей посадок:



```text

36P7 = 36 × 35 × 34 × 33 × 32 × 31 × 30

&#x20;    ≈ 42 072 307 200

```



Количество возможных последовательностей ветров:



```text

8P7 = 8 × 7 × 6 × 5 × 4 × 3 × 2

&#x20;   = 40 320

```



Количество полных партий в наивном дереве:



```text

36P7 × 8P7 ≈ 1.7 × 10^15

```



Наивный полный перебор невозможен.



Поэтому проект обязательно использует:



\* битовые маски;

\* мемоизацию;

\* канонизацию;

\* отсечения;

\* хорошую сортировку ходов;

\* измерение статистики.



Даже с этими оптимизациями нельзя заранее гарантировать, что `6 × 6, k = 7` будет решён на одном CPU за разумное время. Поэтому проект строится как исследовательский инструмент с поэтапным масштабированием.

\## 18. Требования к производительности и памяти



\### 18.1. Память



Одно состояние в чистом виде:



```text

uint64\_t dandelions — 8 байт

uint64\_t occupied   — 8 байт

uint8\_t used\_dirs   — 1 байт

```



Но в hash map реальная стоимость одного состояния будет существенно выше из-за служебных данных.



Ориентировочно:



```text

24–64 байта на состояние или больше

```



Примерные оценки:



```text

100 млн состояний  → примерно 2.4–6.4 ГБ+

1 млрд состояний   → примерно 24–64 ГБ+

```



Поэтому программа должна поддерживать лимит количества состояний и корректное завершение при достижении лимита.



\### 18.2. CPU



GPU не является приоритетом, потому что задача содержит:



\* рекурсивный поиск;

\* ветвления;

\* хэш-таблицы;

\* irregular memory access;

\* множество зависимых состояний.



Один CPU является реалистичной целевой платформой для первой версии.

\## 20. Важные открытые вопросы



Эти вопросы не блокируют первую версию, но должны быть зафиксированы.



1\. Нужно ли в будущем поддерживать `k > 8`?



&#x20;  \* Сейчас предполагается, что нет, потому что направлений всего 8 и они не повторяются.



2\. Нужно ли поддерживать поля больше `8 × 8`?



&#x20;  \* Сейчас приоритет — `n ≤ 8`, чтобы использовать `uint64\_t`.



3\. Нужно ли делать визуализацию стратегии?



&#x20;  \* На первом этапе достаточно JSON/текстового вывода.



4\. Нужно ли искать не только факт победы, но и “насколько уверенную” победу?



&#x20;  \* Например, минимальное число занятых клеток при оптимальной игре игрока 2. Это может быть отдельным режимом в будущем.



5\. Нужно ли исследовать изменённые правила?



&#x20;  \* Например, разрешить повтор направлений, изменить набор направлений, изменить цель или число раундов.

\## 22. Главный принцип проекта



Проект не должен начинаться с попытки сразу “решить `6 × 6, k = 7`”.



Правильный путь:



```text

сначала корректность → затем статистика → затем оптимизация → затем масштабирование

```



Ценность проекта не только в финальном ответе для одного размера поля, но и в исследовательском инструменте, который показывает, как меняется победитель и сложность поиска при изменении параметров игры.
